# Security audit report — nile/core (backend/)

## 1. Run scope and limits

- **Profile:** `quick`, scoped to `backend/` (Go services, Firebase functions, print relay, loadtests). `client/`, `cloudbuild/` and `docs/` were read only where they defined backend contracts. **This is a partial pass, not a clean bill of health.**
- **Source ref:** none. `core` is a Sapling checkout, not a git repository, and the worktree state is unknown.
- **Budget:** none set. Agents used: 4 reconnaissance + 7 hunters + 1 coverage critic + 21 candidate verifiers = 33 (the quick-profile estimate was 15–25; a candidate count of 21 drove the overrun).
- **Execution policy:** source-only. No target code was built or run, and no network or deployed service was contacted. The skill requires a complete OS sandbox, which could not be guaranteed (macOS `sandbox-exec` is present but memory limits are not reliably enforceable), so every runtime-dependent claim is `needs_validation`. **Every "confirmed" finding below is a source-level observation** (a check absent on every path), not a runtime result.
- **Prior runs:** none; nothing carried over.
- **Deviations from the skill:** hunters and verifiers read the skill's method, attack-class and schema files by path instead of having them pasted verbatim into prompts; agent write isolation relied on instructions, not OS enforcement; the quick profile's single critic pass is the only coverage check. Phase 4/5 were merged per the quick profile (one fresh verifier per candidate, none of whom hunted it). Mechanical edits made by the parent: repository-relative path normalisation, trace-step labelling to meet the schema, and one severity cap (`H5-resolvers-no-authz-write`: verifier rated overall `high` above its `medium` demonstrated impact; capped to `medium` per the skill rule).
- **Deferred coverage:** 14 units, listed in section 7.

## 2. Security posture summary

The perimeter around authentication is weaker than the per-user checks suggest. Three independent weaknesses combine: the API admits anonymous callers by **operation name**, many resolvers have **no per-resource authorization** of their own, and several internal/ops endpoints (nilocloud Pub/Sub push routes, Gerrit webhook, internal gRPC identity) trust unauthenticated input. Authenticated users can also **grant themselves roles** through the SetUser form. Some of the most serious potential issues (hardcoded robot token, gRPC identity spoofing, unauthenticated PDF function) depend on deployment facts the repository cannot show and are listed as needs-validation. Signature verification for Slack and Twilio, the Google OIDC robot path, ZPL escaping and relay publisher IAM are sound.

### 3.1 [HIGH] Any authenticated user can set roles and password on a user account via the SetUser form (self-service role escalation, cross-user password reset)

- **Fingerprint:** `H5-setuser-self-role-escalation`
- **Source location:** `backend/go/api/internal/graph/schema.resolvers.go:1146`
- **Lower-trust principal:** A low-privilege authenticated buyer or seller who wants admin-level roles on their own account, or who wants to reset another user's password.
- **Bounded reproduction (not executed):** `mutation { form(input:{type:SetUser, fields:[{id:1,value:"<own email>"},{id:-3,value:"<own firebase uid>"},{id:-2,value:"<own profile id>"},{id:7,values:["Super"]}]}) { ... } }`
- **Conditions:** Attacker needs any valid authenticated session (any party type: buyer, seller or admin). For self-escalation the attacker needs their own firebase UID and profile ID (available to them via the SetUser form or their token). To reset another user's password or roles they need that user's firebase UID, which is not a secret but is not necessarily easy to obtain. Assumes the auth service applies the pushed custom claims to subsequent tokens, which is the evident design. The deployed token refresh behaviour was not observed.
- **Result and impact:** The Form and FormNew GraphQL mutations authorize FormTypeSetUser with an OR of (caller is Admin party type) or (caller's email equals the client-supplied Email form field). The attacker controls that email field, so the check passes for any authenticated user by sending their own email. The same request also carries a separate client-supplied hidden firebase-ID field, a roles multiselect and a password field. The email value is validated as an email but is not tied to the target user ID. handleSetUser passes the fields through customers.UserInput to administrator.UserUpdateInput. The administrator service performs no authorization of its own. It loads the user by the client-supplied ID, calls UpdateUserPassword on that ID, rewrites the roles of that user's DB email via userroles.MatchTx with the client-supplied role list, and pushes the resulting claims to the auth service. The access.Has(ProfileRoles, Write) permission is used only to render the role field in the form UI (customers/user.go:54) and is never enforced on submit. A normal buyer or seller can therefore grant themselves privileged roles (for example RoleSuper) and reset any other user's password by supplying any known Firebase UID.
- **Priority rationale:** likelihood high (Any authenticated user can trigger it with a single GraphQL mutation. The only extra inputs are their own email and UID, and no unusual preconditions were found in source. Deployment facts such as token refresh and any WAF were not observed.) / impact high (Defeats role-based authorization. A user can grant themselves privileged roles (for example Super), and can reset the password of any user whose UID they know, which is account takeover of targeted users. It is not rated critical because it is not unauthenticated and cross-account takeover needs a known target UID.). Confidence high: Every hop was re-read. The OR check, the client-controlled email, the absence of any permission enforcement on submit and the absence of authorization in the administrator service were all verified directly. Runtime effects such as claims refresh were not executed.
- **Smallest fix:** Server-side enforcement: for FormTypeSetUser in both Form and FormNew, allow the call only if the caller is an admin or the supplied firebase ID equals the caller's own UID. Ignore the roles field unless access.Has(ctx, permissions.ProfileRoles, permissions.Write) is true. Require admin, or a current-password or re-auth flow, to change a password, and never for other users. Ideally add an authorization check in the administrator service as defence in depth.

### 3.2 [HIGH] Unauthenticated GraphQL access to any operation by naming it Signup/SignUp/ValidateCurrentToken

- **Fingerprint:** `H5-unauth-opname-bypass`
- **Source location:** `backend/go/api/cmd/server/main.go:120`
- **Lower-trust principal:** Anonymous internet client with no account.
- **Bounded reproduction (not executed):** `POST /query with header Authorization: unauthenticated and body {"operationName":"Signup","query":"query Signup { logisticsDoc(logDocType: SELLER_PACKING_LIST, profileID: 1, date: \"2026-01-01T00:00:00Z\") { info { title } tables { rows { cells } } } }"}`
- **Conditions:** The API GraphQL HTTP endpoint is reachable by the attacker (Cloud Run ingress/IAM not visible in source; the endpoint is the client-facing API). None required: Authorization: unauthenticated plus operationName Signup.
- **Result and impact:** AuthOperation maps the literal Authorization value 'unauthenticated' to a placeholder unauthed user, then only rejects that user when the client-supplied GraphQL operation name is not in a small public allowlist. The operation name is attacker-chosen and independent of the selection set, so any query or mutation can run anonymously by labelling it 'Signup'. No later directive, field middleware or resolver-wrapper blocks the unauthed user, and many resolvers perform no auth.Checks of their own. The unauthed user is propagated to downstream gRPC services, whose server interceptor accepts it without rejection.
- **Priority rationale:** likelihood high (Trivial request, no credentials, deterministic; exposure depends only on the API endpoint being internet-reachable, which is unobserved but expected for a client-facing GraphQL API.) / impact high (Cross-tenant unauthenticated read of shipment/packing-list data including shipping addresses and seller/buyer info, plus unauthenticated invocation of other unchecked mutations (UpdateClaims, UploadPop); full extent across all resolvers not enumerated.). Confidence high: The gate, its name-based allowlist, the absence of other middleware or directives, and a concrete unchecked resolver with real data were all directly read in source; only network reachability is an unobserved deployment fact.
- **Smallest fix:** Enforce the allowlist on the actual root field names (inspect op.Operation.SelectionSet) or use an AroundRootFields/directive that rejects the unauthed user for every field except signUp/validateCurrentToken; also remove the plain 'unauthenticated' sentinel from client-reachable token handling; add auth.Checks to LogisticsDoc, UpdateClaims and UploadPop.

### 3.3 [HIGH] nilocloud /v1/subscriptions/* routes have no effective authentication (discarded r.WithContext result); unauthenticated callers can drive Pub/Sub job dispatch

- **Fingerprint:** `nilocloud/subscriptions-auth-noop`
- **Source location:** `backend/go/nilocloud/internal/handlers.go:18`
- **Lower-trust principal:** Unauthenticated internet client with the nilocloud service URL.
- **Bounded reproduction (not executed):** `POST /v1/subscriptions/nilo with body {"message":{"data":"<base64 of {\"type\":\"nexport-pause-consumers\",\"info\":\"<base64 JSON string of a database name>\"}>","id":"1"},"subscription":"x"} and no Authorization header`; `consumer-unblock variant: data = base64 of {"type":"consumer-unblock","service":"ledger","consumer":"<id>","expected_cursor":<n>}`
- **Conditions:** Attacker must reach the nilocloud Cloud Run URL; source (cloudbuild.yaml --allow-unauthenticated; Slack/Sentry webhooks must also be reachable) indicates it is public, but live IAM/ingress settings were not observed. Attacker needs the service URL and valid job JSON (types/consumer names are visible in the repository).
- **Result and impact:** authMiddleware matches the /v1/subscriptions prefix but its only action is calling r.WithContext(...) and discarding the returned request. No token, secret, or OIDC/JWT check is performed. POST /v1/subscriptions/nilo is wrapped only by this middleware and passes caller-supplied base64 message data straight to handlePubSubMessage, which dispatches privileged ops jobs (nexport pipeline start/pause/export/import/resume, consumer-unblock cursor skipping across six services, mache store restore). POST /v1/subscriptions/cloudbuild is equally open and feeds Slack notification logic. The service is deployed with --allow-unauthenticated in cloudbuild.yaml. Sibling prefixes /v1/webhooks, /v1/events and /v1/mache each do enforce a token, so the missing check on /v1/subscriptions is an outlier. The downstream gRPC Jobs handlers (ledger/administrator ops Jobs) perform no user or role check, so the discarded robot identity is not a hidden control; nilocloud's own gRPC calls carry through, and the job runs regardless.
- **Priority rationale:** likelihood medium (No auth is present on the path in source and the deploy command allows unauthenticated invocation, but the URL must be known and live Cloud Run ingress/IAM was not observed.) / impact high (An unauthenticated caller can pause consumers across all databases, skip stuck events (permanently advancing cursors), trigger mache store restores, and start the nexport data refresh pipeline; this is unauthenticated remote disruption/mutation of shared internal services.). Confidence medium: Missing control is directly visible in source on every path; confidence is capped by unobserved deployment facts (Cloud Run IAM/ingress, whether an upstream proxy enforces auth) and by not tracing every downstream job's data effect.
- **Smallest fix:** Verify the Pub/Sub push OIDC token (google.golang.org/api/idtoken.Validate with audience and expected service-account email) for /v1/subscriptions/*, returning 401 on failure; also set the Cloud Run service to require authentication for these paths where feasible (separate internal service or IAM invoker only for the push service account), and fix the discarded WithContext by assigning `r = r.WithContext(...)` only after verification.

### 3.4 [MEDIUM] editShipment/editShipmentItem authorize by party type only, with no check that the caller's profile is a party to the shipment (cross-tenant write)

- **Fingerprint:** `H5-editshipment-no-ownership`
- **Source location:** `backend/go/api/internal/graph/schema.resolvers.go:1595`
- **Lower-trust principal:** A seller or buyer at tenant A with a valid session who obtains the ID of a shipment between other parties.
- **Bounded reproduction (not executed):** `mutation { editShipment(input:{id:"<other tenant shipment KSUID>", intent:EDIT_FOR_SELLER, ...}) { success } }`
- **Conditions:** Attacker holds a valid authenticated Seller or Buyer session (any tenant). The attacker must know the target shipment's KSUID, which is not enumerable by guessing. Whether IDs leak to other tenants was not established from source. The shipment's type must have a seller or buyer, and the intent must be one for which that party type is allowed. For example, EditForSeller, DispatchSeller, Complete and Cancel on external shipments.
- **Result and impact:** The editShipment and editShipmentItem GraphQL mutations load a shipment by caller-supplied ID and authorize through EditShipmentAuthorised, which only checks the caller's PartyType (admin, or buyer/seller if the shipment type has a buyer/seller). It never compares the caller's ProfileID to the shipment's BuyerID, SellerID or AdminID. The edit is then applied through Ledger.Set or EditOrders with no further identity check. Any authenticated Seller or Buyer who knows another tenant's shipment ID can therefore apply edits, dispatch, receive, cancel or complete intents to that shipment. The sibling read-path check EditShipmentAuthorized, which calls ShipmentAuthorized (IsParty) and CheckRoleMayEdit, exists but is used only by a read query, not by these mutations.
- **Priority rationale:** likelihood medium (Any authenticated buyer or seller can attempt it. The attacker needs a valid shipment KSUID for another tenant, which is not guessable, and exposure of such IDs to other tenants is unobserved. Intents are also limited by shipment type.) / impact high (Cross-tenant write to shipments, covering edits, dispatch, receive, cancel and complete state changes on orders belonging to other parties.). Confidence high: The absent ownership check was verified in the resolvers, EditShipmentAuthorised, auth.Checks/PartyTypes, fetchLedgerShipment and the edit handlers. Ledger.Set takes no user identity. Not run. The ID-disclosure prerequisite is unverified, which is why likelihood and overall severity are held at medium.
- **Smallest fix:** Call ShipmentAuthorized(ctx, smt) (or use EditShipmentAuthorized with IsParty) in EditShipment, EditShipmentItem and the shipment_edits.go:519 path before any edit. Admins remain exempt via party-type logic. Consider enforcing ownership inside the shared editShipment entry too, and add a regression test with a non-party seller and buyer.

### 3.5 [MEDIUM] Packhouse allocation mutations accept any seller's sellerID from any Seller/Admin user (ID binding is dead code)

- **Fingerprint:** `H5-packhouse-any-seller`
- **Source location:** `backend/go/api/internal/graph/schema.resolvers.go:1015`
- **Lower-trust principal:** A seller-party user with a packhouse role, for example a packhouse operator at one seller, calls the mutation with another seller's profile ID.
- **Bounded reproduction (not executed):** `mutation { packhouseClearInventories(sellerID: <victimSellerID>) }`; `mutation { packhouseSetAllocation(input:{sellerID:<victimSellerID>, allocations:[...]}) }`
- **Conditions:** Authenticated user with party type Seller (or Admin). The user must hold a role granting PackhouseAllocations/Write (Packhouse, PackhouseWorker, Tech or Super). PackhouseItemMixed additionally requires a native farmer app origin (auth.IsNativeFromContext). A victim seller with products must exist. Another seller's ID must be known or guessable (int64 profile ID).
- **Result and impact:** PackhouseSetAllocation, PackhouseItemAllocations, PackhouseItemMixed and PackhouseClearInventories authorize with auth.Checks(PartyTypes(Admin, Seller), PartyTypeForID(sellerID)). auth.Checks has ANY semantics and PartyTypeForID is called without party types, so it can never be true. Any authenticated Seller therefore passes the first check for every sellerID. The only other gate is the role permission PackhouseAllocations/Write, which is global and not bound to a seller. A Seller-party user holding a Packhouse or PackhouseWorker role (or a Tech or Super role) can set or clear another seller's packhouse stock and allocations in the ledger.
- **Priority rationale:** likelihood medium (Requires a Seller-party user with a packhouse-type role and knowledge of a victim seller ID. Who holds these roles in production is not visible in source.) / impact medium (Cross-seller write and clear of packhouse stock and allocation ledger data, which can disrupt another seller's inventory and orders. No data read and no account takeover.). Confidence high: The semantics of Checks, PartyTypes and PartyTypeForID were re-read directly. The sellerID flows unbound to the trader and ledger calls, and no other control was found on the path.
- **Smallest fix:** Require ownership for seller callers. Allow Admin for any seller, and for Seller allow only PartyTypeForID(sellerID, PartyTypeSeller). Replace the broad PartyTypes(Seller) check with that, and add a regression test for cross-seller calls.

### 3.6 [MEDIUM] Read resolvers LogisticsDoc, TableDialog, ShipmentDispatchDialog (and seller-side QualityReport) lack any ownership check, exposing other tenants' shipment data to any authenticated user

- **Fingerprint:** `H5-resolvers-no-authz-read`
- **Source location:** `backend/go/api/internal/graph/schema.resolvers.go:2786`
- **Lower-trust principal:** An authenticated seller or buyer on the platform queries another tenant's profile or shipment.
- **Bounded reproduction (not executed):** `query { logisticsDoc(type: <SELLER_PACKING_LIST enum>, profileID: <victim profile id>, date: "<dispatch date>") { ... } }`; `query { tableDialog(type: SETTLEMENT, shipmentID: "<victim shipment id>") { ... } }`; `query { shipmentDispatchDialog(shipmentID: "<victim shipment id>") { ... } }`
- **Conditions:** Valid authenticated Buyer or Seller account. Admin is not required. QualityReport additionally needs a Seller account. TableDialog, ShipmentDispatchDialog and QualityReport need a victim shipment KSUID, which is not guessable and must be obtained from another channel. LogisticsDoc needs only a victim profileID (an int64, enumerable) and a dispatch date with matching created-status shipments.
- **Result and impact:** Several GraphQL Query resolvers in backend/go/api/internal/graph/schema.resolvers.go take a client-supplied profileID or shipmentID and return data without any role check or ownership check. The Ledger.Shipments read path has no caller scoping. Per resolver: LogisticsDoc (:2786) has no auth.Checks, uses the client profileID directly as a ledger filter, and returns another seller's packing list including buyer shipping addresses. TableDialog (:2922) has no auth.Checks and no ShipmentAuthorized/IsParty check, and returns settlement, payment and charge dialogs with amounts and shipment names for any shipment ID. ShipmentDispatchDialog (:2994) has no checks and returns shipment name, case count and the destination street and city for any shipment ID. QualityReport (:4245) checks party type only (Seller or Admin, Buyer blocked) with no ownership check, so any Seller can read another party's inspection report, seller label and delivery address. Not established as a meaningful leak: ShipmentTransactions (:2880) has no authz but shipmentTransactionsTable skips any transaction not involving the caller's profile (accounts.go:135) and shipmentTotalsInfo is admin-only, so it only leaks the shipment name and open state. DocumentNumber (:4203) is restricted to Seller/Admin and returns only a document number; it has no ownership check, but the impact is trivial. Authenticated-user impact only; anonymous reach is a separate candidate.
- **Priority rationale:** likelihood medium (Any authenticated account can call these. LogisticsDoc is enumerable through integer profile IDs, but the shipment-ID-based resolvers need an unguessable KSUID that must leak elsewhere.) / impact medium (Cross-tenant read of packing lists, buyer addresses, settlement and payment amounts and inspection reports. There is no write or code execution and no secrets.). Confidence high: Every cited resolver was re-read and no authorization or scoping exists on the path (resolver, helper, ledger and middleware). Deployment facts were not needed for the missing check itself.
- **Smallest fix:** Add per-resource authorization to each resolver. For LogisticsDoc, require auth.PartyTypeForID(profileID, Seller) or Admin. For TableDialog, ShipmentDispatchDialog, QualityReport, ShipmentTransactions and DocumentNumber, call ShipmentAuthorized(ctx, shipment) unless the caller is Admin. Consider restricting the settlement and payment dialogs to Admin.

### 3.8 [MEDIUM] PotatoesSA export-only token user can run any Admin-party-type query because the scope gate only inspects the first top-level field that has an argument

- **Fingerprint:** `auth/potatoessa-scope-first-field-only`
- **Source location:** `backend/go/auth/auth.go:373`
- **Lower-trust principal:** A holder of the PotatoesSA token, who should only be able to fetch the export URL, sends one GraphQL query that begins with the allowed exportData selection and appends Admin-readable fields for other tenants.
- **Bounded reproduction (not executed):** `query { exportData(type: PotatoesSA) seller(sellerUUID: 1, search: "") { __typename } }`
- **Conditions:** The caller must present the PotatoesSA token. That is the legitimate partner holder, or anyone who has read it from the source repository or build artifacts. The request must reach the api GraphQL endpoint with X-Platform set to the Nile admin id so that checkPlatform passes. Whether the endpoint is publicly reachable is not determined from source. Only query operations are reachable, because the gate map is keyed to 'query'. Resolvers that also require role-based access.Has permissions are not reachable, because the user has no roles.
- **Result and impact:** The hardcoded PotatoesSA token resolves to a user with Admin party type and the Nile admin profile id (no roles). The only thing restricting it to the exportData query is isExportDataQuery(), which is called from AuthOperation. That function loops over the operation's top-level selections, skips any field with no arguments, and returns at the first field that has an argument, using only that field's authorisedExternalQueries lookup. It never looks at the remaining selections. A single query document such as `query { exportData(type: PotatoesSA) seller(sellerUUID: 1, search: "") { ... } }` passes the gate. A document that starts with argument-less top-level fields also passes, because those fields are skipped. gqlgen then executes every top-level field with the PotatoesSA user in context. Resolvers guarded only by auth.PartyTypes(Admin) admit that user. Examples are Seller (any sellerUUID), Buyer (any filter.ID), AccountTransactions and OrderStatementEntries. These are read-only query fields, because the gate pins the operation type to 'query'. The scope-limiting control is therefore fully defeated for query operations. Resolvers that also require role permissions through access.Has() are not reachable, because the user has no roles.
- **Priority rationale:** likelihood medium (The path is trivially exploitable once the token is held, but the token is a partner credential that is also hardcoded in source. Whether the GraphQL endpoint is reachable by the token holder is a deployment fact not seen in source.) / impact high (It turns an export-only credential into read access to every query resolver gated only by Admin party type, including cross-tenant seller and buyer data and ledger and accounting data. Mutations and role-gated resolvers are not reachable.). Confidence high: The control flow of the gate and the resolver checks were read directly. The remaining uncertainty is deployment reach and which Admin-only resolvers return meaningful data.
- **Smallest fix:** Replace the first-field heuristic with a strict check. Require every top-level selection (resolving fragments and rejecting non-Field selections safely) to be exportData with the PotatoesSA argument, and reject if any other selection exists. Better still, remove the Admin party type from this user, or add an explicit deny for IsPotatoesSA in resolvers or a gqlgen directive. Also move the token out of source and rotate it.

### 3.9 [MEDIUM] Gerrit webhook Cloud Function is public and accepts forged events without any authentication, enabling attacker-chosen staging deploys

- **Fingerprint:** `gerrit-webhook-unauthenticated-event-forgery`
- **Source location:** `backend/go/gerrit/functions/webhook/webhook.go:62`
- **Lower-trust principal:** Anonymous internet caller who knows the webhook function URL.
- **Bounded reproduction (not executed):** `POST <function-url> {"type":"change-merged","change":{"number":<n>,"branch":"master","subject":"x"},"patchSet":{"number":1},"newRev":"<fetchable-commit-sha>"}`
- **Conditions:** None required to call the function; attacker needs only the function URL (not secret, deterministic cloudfunctions/run.app URL). For arbitrary code to reach staging the attacker needs a SHA fetchable from code.nile.ag by the bot (e.g. a pushed unreviewed refs/changes patchset, which requires a Gerrit account, or any existing unmerged/merged SHA). Without a Gerrit account the attacker can only replay existing commits, supersede/disrupt legitimate staging deploys, and spam builder tasks. Only staging is auto-targeted by this path; production deploys are manually requested and not reachable via this event. Cloud Run ingress is not restricted in the Terraform (no ingress setting found).
- **Result and impact:** The gerrit-webhook Cloud Function is granted roles/run.invoker to allUsers, justified by a comment claiming Gerrit verifies calls via HMAC. The handler never verifies any signature, secret, OIDC token or source IP. It dispatches purely on the body-supplied 'type'. A forged change-merged event with branch master and an arbitrary newRev makes the function record that SHA as staging's targetSha and enqueue a staging deploy of it. The builder agent then fetches and hard-resets to that ref and deploys it to staging, bypassing Gerrit review/submit. Forged patchset-created, nightly-* and reconcile-verifies events can also trigger builder work.
- **Priority rationale:** likelihood medium (Fully unauthenticated and trivial to send, but requires knowing the function URL and, for attacker code, a Gerrit account to produce a fetchable unreviewed SHA; Gerrit fetch-by-SHA policy is not visible in source.) / impact medium (Bypasses review to deploy an attacker-chosen commit to staging and disrupts the deploy pipeline; production not directly reachable, so blast radius limited to staging and builder resources.). Confidence high: Absence of auth is directly visible in the handler, terraform IAM binding and scheduler config; the only uncertainty is deployment facts limiting which SHAs the agent can fetch.
- **Smallest fix:** Remove allUsers invoker. Require authentication: configure Gerrit webhook with a shared secret and verify the HMAC (constant-time) over the raw body in Handle before parsing, and give Cloud Scheduler an oidc_token with an invoker-only service account. Additionally, in handleChangeMerged confirm via the Gerrit API that NewRev is the merged tip of master for the given change before recording/deploying.

## 6. Hardening notes and positive patterns

**Hardening (not findings):**
- No token revocation check on the hot path (`VerifyIDToken`, `auth.go` ~519/543); disabled users stay valid until the token expires.
- `isSubscriptionQuery`/`isExportDataQuery` use unchecked type assertions (`auth.go` ~303-332, 386-387); a fragment-first operation panics per request (gqlgen recovers, 422).
- No HTTP server timeouts or body limits anywhere (`api/cmd/server/main.go:303`, nilocloud); unbounded `io.ReadAll` in Slack, Cloud Build, Twilio and Gerrit handlers, some before signature checks.
- Token comparisons use `!=`, not constant time; the nilocloud webhook token travels in the URL query string; `/v1/mache` reads a different env var with no empty-token guard.
- Public GraphQL `Signup` has no email-domain or invitation check (unclaimed-email pre-registration); `signupBlocking.ts` / `onCreateFirebaseUser.ts` use `email.includes('@nile.ag')` and inspect only `providerData[0]`.
- fortknox encrypts third-party passwords with AES-CTR and no MAC (TODO: security review outstanding in source); keys are a raw env string. Currently only server-written, so not exploitable as found.
- Gerrit agent: `curl https://mise.run | sh` unpinned, unauthenticated `/status` and `/disks` on :9099, `git fetch origin <ref>` without `--`, Cloud Build images tag-pinned not digest-pinned, builder SA has broad roles and is also the runtime identity of the public webhook function.
- Relay SA holds project-wide `roles/datastore.user`; print jobs are published by the shared default compute SA; `provision-pi.sh` grants NOPASSWD sudo and pipes get.docker.com to sh (operator-run).
- `generatePdf`: `browser.close()` skipped on error paths (Chromium leak), no max-instances; footer HTML injection via `name`.
- Introspection and the playground are enabled in all environments; no GraphQL complexity limit; `LogoCache.fetch` reads responses without a size cap.
- Hardcoded secrets in source beyond the robot token: the PotatoesSA token (`auth.go:31`), the robot token also in `pdf.ts`, loadtests, and client files. **Rotate once confirmed live.**

**Positive patterns:** Slack request signing uses slack-go with a 5-minute window and constant-time compare; Twilio webhook HMAC cannot be forged by header spoofing; `robot_oidc.go` validates signature, audience, SA email and verified flag and refuses outside cloud; `AuthHTTP` and `/docs/pdf` run as the caller and reject unauthenticated/PotatoesSA tokens; `gerrit-build` is restricted to the builder SA; the relay topic has a single trusted publisher, per-hub subscription filters, and ZPL control characters are stripped in `ledger/label/label.go`; many resolvers do pin non-admin callers to their own profile; `checkUser` blocks self-registered Nile admin accounts in production.
